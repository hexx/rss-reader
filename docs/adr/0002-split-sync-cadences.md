# 同期を「新着取り込み(30分)」と「フル同期(3時間)」の2カデンサに分割し、同期の1回あたり記事上限を撤廃する

新着記事の鮮度（公開→要約付き表示の遅延）を高めるため、定期同期を2本の Cron Trigger に分割する。`*/30 * * * *` は新着記事の取り込み専用（既存記事のはてなブックマーク再取得＝バックフィルはしない）、`0 */3 * * *` は新着取り込み＋全フィード記事のバックフィルを行うフル同期。`scheduled` ハンドラで `event.cron` を見て分岐する。あわせて同期の1回あたり記事上限（Cron の旧 `CRON_MAX_PER_SITE = 10`、手動の旧 `MANUAL_MAX_PER_SITE = 2` / `MANUAL_MAX_TOTAL = 2`）をすべて撤廃し、新着記事を全件処理する。上限しか役割のなかった `isCron` パラメータも削除し、同期の差は `includeBookmarkBackfill` のみで表現する。

## 決定内容

- Cron を2本登録し、`event.cron === '0 */3 * * *'` のときだけ `includeBookmarkBackfill = true`（バックフィル実施）。30分 cron は `false`。
- `syncSite` / `syncAllSubscriptions` に `includeBookmarkBackfill`（既定 `true`）を追加。手動同期（`/api/sync`）は従来どおりバックフィルありの挙動を維持。
- 1回あたりの記事上限を Cron・手動とも撤廃（`CRON_MAX_PER_SITE` / `MANUAL_MAX_PER_SITE` / `MANUAL_MAX_TOTAL` と break ロジックを削除）。上限の切り替え専用だった `isCron` パラメータも削除。
- 排他ロックは導入しない。処理は記事単位の逐次 INSERT で、`articles.url` UNIQUE と `(article_id, user)` UNIQUE により冪等。実行が重複・中断してもデータ重複やロスはなく、次回実行で再開する。

## Considered Options

- **単一 Cron（3時間）のまま新着上限だけ撤廃**: 新着の鮮度が3時間刻みのまま改善せず不採用。
- **20分単一 Cron**: 全既存記事のバックフィルが約9倍の頻度で走り、はてなへのリクエスト量と Worker 実行時間が跳ね上がる。目的（新着の鮮度）に対して過剰なため不採用。
- **バックフィルを「直近7日」で絞る**: 採用を見送り。バックフィルの走査対象は DB 全件ではなく「RSS フィードが今載せている記事」に閉じており（`fetchRssOrFallback` はフィード全件を返す）、記事总数（約1万件）はコストに効かない。7日窓は実効的な削減にならないため YAGNI と判断。
- **記事上限（Cron/手動）を維持**: 上限はタイムアウト防止が目的だが、冪等な逐次処理がタイムアウトを自然に吸収する（中断→次回再開）ため冗長。Cron は wall 15分、手動は HTTP `waitUntil` の30秒が本当の上界で、明示上限（特に手動の2件）はほぼ形骸化していた。むしろ初回購読時のバースト取り込みを遅らせるだけなので撤廃。これにより `isCron` も不要になり API が簡素化される。

## Consequences

- Workers Paid プランが前提。Cron Trigger の CPU 時間は**間隔が1時間未満で30秒、1時間以上で15分**、wall 時間はいずれも15分が上限。つまり30分 cron（取り込み専用）は CPU 30秒、3時間 cron（フル同期）は CPU 15分。記事処理の大半は I/O 待ち（fetch・はてなのレート制限 sleep・AI 呼び出し）で CPU 時間に算入されないため、30秒 CPU でも定常的な新着数なら余裕がある。
- 初回購読や高負荷フィードで大量の新着が一度に発生すると、30分 cron が wall/CPU 上限で中断され得る。ただし冪等なので次回以降の30分実行で段階的に完走する（データロスなし）。旧上限（10件/回）より早く完走する。
- 30分 cron と3時間 cron が同時刻（毎時0分など）に重なる場合があるが、冪等性により重複は UNIQUE 違反→warn ログで吸収され、多少の AI 呼び出し無駄打ちにとどまる。
- 手動同期（`/api/sync`）は HTTP `waitUntil`（最大30秒）で動作し、クライアントは4秒後に再読み込みする fire-and-forget。上限撤廃後は「30秒で処理できる分（数件）」が1回の取り込み量の実質上限となり、従来の2件上限と体感はほぼ変わらない。完了通知（ポーリング/SSE 等）は未実装で、別途改善余地がある。
