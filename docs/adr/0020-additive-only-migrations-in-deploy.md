# マイグレーションはデプロイ手順に組み込み、追加のみを規約とする

2026-09-06 のデプロイで、`articles` に列を追加するマイグレーション `0007_curvy_wolf_cub.sql` を本番 D1 に適用しないままコードだけを反映した結果、以降すべての新着 INSERT が `table articles has no column named content_backfill_failures: SQLITE_ERROR` で失敗し、約 1 日気づかれなかった（`docs/specs/ingest-failure.md` §7）。原因は「コードの反映」と「スキーマの反映」が別の作業として運用者に委ねられていたこと。

## 決定

- **本番反映の手順（`npm run deploy`）は `wrangler d1 migrations apply rss-reader --remote` → `wrangler deploy` を 1 回の実行でこの順に行う**。Workers Builds の deploy command がこれを呼ぶ（ADR-0019）。`migrations apply` は適用台帳（`d1_migrations`）を見るため冪等で、未適用が無ければ何もしない。
- **API トークンは D1 Edit 権限を含むカスタムトークンを使う**。Workers Builds が自動生成するトークンの権限に D1 は含まれない。
- **マイグレーションは追加のみ（後方互換）とする**。`DROP` / リネームなど後方互換でない変更は「① 追加してコードから使う → ② 旧列を消す」の二段構えにし、第二段は必要になった時点で Issue 化して実施する。不要になった列は残すことを既定とする（消さなくても実害が小さい）。
- 理由: 適用はコードの反映より先に走るため、「旧コード + 新スキーマ」で動く時間帯が必ず生じる。この時間帯で壊れないことが自動適用の前提条件である。
- **プレビュー配備にはマイグレーション適用を入れない**（プレビュー配備自体を採用していない。ADR-0019）。
- **ローカルからの実行は `WORKERS_CI=1` を要求する**（`scripts/deploy-guard.mjs`）。手順を 1 つにして順序を守らせる一方、抜け道は明示的なフラグに閉じる。

## Considered Options

- **乖離検知のみ（CI で未適用を検出して失敗させ、適用は人手）**: 人手の適用操作が残るため「忘れる」経路が消えない。issue の選択肢 (b) はこれ。
- **CI（GitHub Actions）に本番 D1 との乖離検知も追加**: 本番反映が唯一の適用経路になる以上、通常は乖離しない。Cloudflare の認証情報を GitHub に置く必要もあり、いまは採用しない。**乖離が起きたら、それは経路を外れた反映が起きた証拠**として扱う。
- **破壊的 DDL を CI で機械的に検出**: `DROP INDEX` のような安全な変更も含む誤検知が多く、破壊的変更が稀である以上コストに見合わない。第二段の実施は Issue 運用で担保する（ADR-0004 の流儀）。
- **ダッシュボードに長いコマンドを直書き**: 「ダッシュボードの設定が実体」になり、リポジトリと乖離しても気づけない。実体はリポジトリのスクリプトに置き、ダッシュボードは `npm run deploy` を呼ぶだけにする（同じ罠の[実例](https://github.com/Egger0/cs2cup/issues/96)）。

## Consequences

- D1 は巻き戻せない。コードのロールバック（revert）では D1 は戻らないが、追加のみ規約により旧コードは新スキーマで動く。
- 初回の Workers Builds デプロイでは、既に適用済みのため「適用なし」で素通りするのが期待挙動であり、これをログで確認する（`docs/specs/deploy.md` §8）。
- 後方互換でない変更が本当に必要になったときは、二段目のデプロイを忘れないための Issue を必ず立てる。
