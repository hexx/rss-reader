# Issue ステータスの確定運用

issues/ の Issue ファイルは issue-logger テンプレート準拠のためフロントマターが `title` / `status` / `created` の 3 字段しかなく、ステータス値だけでは「なぜその状態か」が後続エージェントに伝わらない。そこで、ステータスを確定（監査・棚卸し）する際の判定基準と記録方法を次の通り決めた。

- **別 Issue で実現済みの要求は DONE**: 本文に実現元 Issue を追記する。SUPERSEDED のような新ステータスは設けない（4 値の互換性を維持）。
- **複数要求の一部のみ実装は TODO のまま**: 本文を未達要求へ狭める（All-or-nothing）。ファイル分割はしない。
- **WONTFIX は「価値喪失」または「技術的前提の陳腐化」の二軸**で判定する。期限による機械的な切り捨てはしない。
- **根拠は本文末尾の「## 解決記録」セクションに追記**する。フロントマターは拡張しない（issue-logger テンプレートおよび他環境エージェントとの互換性維持）。
- **確定作業は監査（コード照合による実装済み検出）→ 棚卸し（残 TODO の価値・前提判定）の順**で行い、結果はカテゴリ別バッチでオーナーに承認してもらう。

## Considered Options

- フロントマターに `updated` / `resolution` を追加する案: 機械可読になるが、issue-logger テンプレートから逸脱し他環境との互換性が壊れるため不採用。
- SUPERSEDED / DUPLICATE を 5 値目として追加する案: 語彙と issue-logger スキルとの互換性コストに対し、DONE + 本文追記で表現可能なため不採用。
- 部分 DONE を認める / 未達部分を新ファイルへ分割する案: ステータス語彙の曖昧化やファイル ID 参照ルールの破壊を招くため不採用。
