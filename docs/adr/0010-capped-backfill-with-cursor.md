# はてブ補完（Backfill）を 1 回 60 件＋補完カーソルの巡回に変更する

購読 14 Source のフィード掲載件数を実測すると 1 pass 合計 349 件で、フル同期（`0 */3 * * *`）は既存記事ごとに はてブ補完として jsonlite を叩くため 1 回約 330 本になる。現行のリミッター間隔（1〜3 秒）でも待機だけで約 11.7 分になり、cron の wall 上限 15 分（ADR-0002）にほぼ張り付いていた。さらにこの大量アクセスが共有エグレス IP 宛の時間 quota を枯らし、後続の RSS 取得 429 の主因であると推定される（**未検証の仮説**。本番ログ観察での成否判定は今回の受入条件に含まない）。

## 決定内容

- **はてブ補完は 1 回の同期あたり 60 件を上限**とする（新着記事に対するブックマーク取得は上限の対象外。新着は必ず取得する）。
- **Source ごとに Backfill Cursor（補完カーソル）を持ち**、前回補完を始めた位置の次から巡回する。カーソルはフィード掲載順に対する進行位置で、**末尾に達したら 0 に折り返す**。保存先は `subscriptions.backfill_cursor`（integer、既定 0、購読行の削除とともに消える）。
- **補完の遅れは Freshness Budget の対象外**とし、別予算 **Completeness Window（補完完走ウィンドウ）≤ 24 時間**を約束として置く。根拠: 349 件 ÷（60 件 × 8 回/日 = 480 件/日）≒ 全周 18 時間。
- **カーソルは Source 側に置く唯一の進行状態**である。律速状態（次回取得可能時刻・連続障害数）は取得枠（`fetch_buckets`）だけを持ち、Source 単位の状態は持たない（ADR-0009）。将来「誰かが」Source 側の律速列を `subscriptions` に追加しに来たときは、この区別を壊さないこと。

## Considered Options

- **1 回 60 件だが毎回フィード先頭から**: フィード末尾の記事が構造的に永久に補完されないため不採用。
- **補完対象を直近 D 日に限定**: **ADR-0002 の「7 日窓は YAGNI」という却下判断をここで supersede する**。あの判断は「走査対象はフィードが今載せている記事に閉じており記事総数はコストに効かない」という前提で、jsonlite のリクエスト本数を主因と見ていなかった。今回は本数が主因なので、上限＋巡回で抑える。
- **上限なしのまま間隔だけ厳格化**: wall 15 分接近（11.7 分）が残り、quota 枯渇も減らない。
- **N=150（全周 約 7 時間）**: 1 run の jsonlite 待機が約 7.5 分（はてな群 3〜6 秒）になり wall 上限との距離が縮まりすぎる。24 時間予算で足りるので見送り。

## Consequences

- 記事のはてブコメント・Hatena Summary が揃うまで最大 24 時間かかるケースが出うる（現行は最悪 3 時間）。新着の鮮度約束は変わらない。
- Hatena Summary の AI バックフィル上限（20 件/run）とは別枠の上限であり、両方を満たす進行になる。
- カーソルは Source 単位なので、同じ相手を複数購読していても補完位置が食い違うことはない（群を跨ぐ総量制御は ADR-0009 の取得枠が担う）。
