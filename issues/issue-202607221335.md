# 課題解決プロンプト: はてなブックマークコメントの並びを時系列・新しい順に統一する

## 1. 役割定義 (Persona)
あなたは高度なソフトウェアエンジニアです。以下のコンテキストとゴールを基に、正確かつ効率的な修正を行ってください。用語は `CONTEXT.md`（Bookmark / Bookmark Timestamp / Hatena Summary）に従うこと。設計判断の根拠は `docs/adr/0003-bookmark-comment-ordering.md` を参照。

## 2. 背景・前提条件 (Context)

### ユーザー報告
「はてなブックマークのコメントの並びを本家と同じか、本家の逆順にしたい。現在は順不同に見えちゃう」

### 根本原因（調査済み）
`src/services/hatena.ts` の `parseHatenaTimestamp` は jsonlite の `timestamp` を **epoch 秒文字列**と仮定して `Number.parseInt(value, 10)` している。しかし実際の API（`https://b.hatena.ne.jp/entry/jsonlite/?url=...`、curl で確認済み）は **`"2025/07/21 09:41"` 形式の日時文字列（JST・分精度）**を返す。

- `parseInt("2025/07/21 09:41")` = `2025` → `new Date(2025 * 1000)` = **1970-01-01T00:33:45Z**
- 全ブックマークの `createdAt` が 1970 年付近に潰れ、`ORDER BY createdAt` が意味を失い「順不同」に見える。

### 確認済みファクト
- jsonlite の生レスポンスの `bookmarks` 配列は**新しい順（降順）**で並ぶ。
- 本家エントリーページのデフォルトは「注目コメント順」（非公開アルゴリズム、jsonlite にスコア無し＝**再現不能**）。再現可能なのは時系列（新着順）まで。
- サーバー（`src/worker.ts` の `fetchBookmarksByArticleIds`）は `orderBy(asc(hatenaBookmarks.createdAt))` で返し、クライアント（`ArticleCard.tsx`）は並び替えせず（コメント非空でフィルタするだけ）。
- `src/workflows/sync.ts` の `persistBookmarks` は `onConflictDoNothing`（先勝ち）。既存行は再同期では更新されない。`id` は `crypto.randomUUID()`（順序情報なし）。
- timestamp は**分精度** → 人気エントリーでは同一分に複数件が並ぶ。

### グリリングで確定した設計決定（ADR-0003）
1. **並びの定義**: 「本家と同じ」＝時系列・**新しい順（降順）**。注目順は再現しない。方向切替UIは付けない（YAGNI。古い順は将来必要になったら別途）。
2. **既存データ修復**: upsert を `onConflictDoUpdate`（`createdAt`, `comment` を上書き）に変更し、次回バックフィル同期で自然治癒させる。一次性マイグレーションはしない。
3. **tiebreak**: `ORDER BY createdAt DESC, rowid ASC`（SQLite 暗黙 rowid。スキーマ変更なし。同一分内は jsonlite 生順序＝新着順と整合）。
4. **タイムゾーン**: `"YYYY/MM/DD HH:MM"` を JST として確定パース（`"YYYY-MM-DDTHH:MM:00+09:00"` へ正規化）。UTC 環境の Workers でも表示・順序が正しくなる。

### 関連ファイル/コード
- `src/services/hatena.ts` — `parseHatenaTimestamp`（パース修正の主対象）、`HatenaBookmarkComment.timestamp` の doc コメント（「epoch 秒」の記述が実態と不一致なので更新）
- `src/worker.ts` — `fetchBookmarksByArticleIds` の `.orderBy(asc(hatenaBookmarks.createdAt))`（L233 付近）
- `src/workflows/sync.ts` — `persistBookmarks` の `.onConflictDoNothing(...)`
- テスト: `src/services/hatena.test.ts`, `src/worker.test.ts`, `src/workflows/sync.test.ts`

## 3. 解決すべきゴール (Goal & Objective)
- [ ] **G1（パース修正）**: `parseHatenaTimestamp` を `"YYYY/MM/DD HH:MM"`（JST）形式に対応させる。`"YYYY-MM-DDTHH:MM:00+09:00"` へ正規化して `new Date` する。不正/欠落値は従来どおり `fallback`（現在時刻）を返す。厳密な正規表現で検証し、マッチしない値を `new Date` の曖昧パースに渡さないこと。
- [ ] **G2（並び順）**: `fetchBookmarksByArticleIds` を `ORDER BY createdAt DESC, rowid ASC` に変更する（drizzle: `desc(hatenaBookmarks.createdAt)` と `sql\`rowid\`` の asc）。クライアントへは新しい順で届く。
- [ ] **G3（自然治癒）**: `persistBookmarks` を `onConflictDoUpdate({ target: [articleId, user], set: { comment, createdAt } })` に変更する。再取得で既存行の `createdAt`（と編集された comment）が最新化されること。
- [ ] **G4（ドキュメント整合）**: `HatenaBookmarkComment.timestamp` 等、実態と合わないコメント（「epoch 秒」等）を更新する。
- [ ] **G5（テスト）**:
  - `hatena.test.ts`: 新形式パース（JST 確定、例: `"2025/07/21 09:41"` → `2025-07-21T09:41:00+09:00`）、不正値/空値の fallback、分精度。
  - `worker.test.ts`: 降順＋同一分 tiebreak（rowid 昇順＝挿入順）の決定性。
  - `sync.test.ts`: 同一 (articleId, user) の再投入で `createdAt`/`comment` が更新されること（DO UPDATE）。
- [ ] 既存テストを壊さないこと（`npm run test`）、`npm run build` が通ること。
